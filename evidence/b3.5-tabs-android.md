# B3.5 Tabs: Android Evidence

## Status

`ANDROID_PLATFORM_IMPLEMENTED_PUBLIC_RPK_BLOCKED_BY_UPDATE_BINDING_NUMBER`

The Android Tabs host mapping, initial mount, and platform input path are
implemented and verified with the real RPK. Full controlled-state acceptance is
blocked by the shared JS ABI validator for numeric `updateBinding` values.

## Android implementation

- Host component type `Tabs` maps to an Android `LinearLayout`.
- `items` creates platform-owned tab labels inside that one host view.
- `selected` is controlled by the existing MountTransaction path.
- User switching emits the existing EventSink `change` event with:
  `numberName=index`, numeric `index`, and string `value`.
- The JS/Core state write-back is expected to produce the next controlled
  `selected` Mount property; no platform business state or second Runtime Tree
  was introduced.
- Removing the Core Tabs node removes its platform tab children; surface close
  clears the host and all child listeners.

## Current blocker

`quickapp-runtime-js/src/abi/runtime_abi_codec.cpp` still validates an
`updateBinding` value as only `string | boolean`; it does not accept `double`,
although `validBindingMap` and the frozen Tabs contract accept numeric values.
The generated Tabs transaction therefore cannot submit the numeric binding for
`selected`. This is a shared JS/ABI defect, not an Android platform defect.
Android must not work around it with platform-local application state.

Once the shared validator accepts numeric `updateBinding` values, rerun the
same RPK and verify:

1. Home mount and selected index `0`.
2. User switches to `任务` and `我的`.
3. `change({index, value})` reaches JS.
4. JS state write-back produces controlled selected updates.
5. Repeated switching and surface teardown leave zero Android nodes/surfaces.
